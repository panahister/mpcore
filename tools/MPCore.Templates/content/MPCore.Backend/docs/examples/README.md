# Examples

Everything here is **illustration only**. These are not requirements for this project, no code from
them should be generated into it, and none of them is a decision anyone has approved.

They exist to show the *shape* of a well-formed requirement and the reasoning that follows from it —
so that when you bring your own capability, you can tell whether it is specified well enough to build.

- [Cancelling a reservation](reservation-cancellation.md) — a state transition with an idempotency
  requirement and an ownership check.

When you bring a real requirement, the assistant is instructed to restate it, list the ambiguities,
and ask you about them rather than filling gaps by inventing rules. That is the behaviour you want:
an assistant that guesses produces work you then have to delete.
