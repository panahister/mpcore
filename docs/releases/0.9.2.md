# MP Core 0.9.2

A patch version: additions only. It follows [0.9.1](0.9.1.md).

Asked for by running the [Tiffin sample](https://github.com/panahister/mpcore-tiffin-sample): a service
that calls another on behalf of a tenant worked for nobody there (finding T-05). ADR-014 has the decision,
in its addendum of 2026-09-28.

## Moving from 0.9.1

Nothing to do. Every change is an addition; a host that configures nothing behaves as before, and no
header is believed.

## New

| Package | What it adds |
|---|---|
| `MPCore.Tenancy.Abstractions` | `TenantHeader`: the header `x-tenant-id`, and what a tenant name is |
| `MPCore.Resilience.Http` | **The tenant of a call.** `AddMPCoreTenantPropagation()` on a client's builder writes the tenant of the work into `x-tenant-id`, on REST and on gRPC clients built by the factory. The package now references `MPCore.Tenancy.Abstractions` |
| `MPCore.Security.AspNetCore` | `TenantClaimOptions.TrustedServiceClients`, and `AddMPCoreTenancyFromClaim(Action<TenantClaimOptions>)`. The header is believed only from a service whose client id is listed, never from a user, never over a tenant in the token |

## Documented

| Package | What it now says |
|---|---|
| `MPCore.Security.AspNetCore` | When a caller is a service: a `client_id` claim, and no user name or a `service-account-` one. The summary said something else. Keycloak 25 and later write `client_id` only for a client with the `service_account` scope |
