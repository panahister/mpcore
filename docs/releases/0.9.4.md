# MP Core 0.9.4 (not yet released)

The next version after [0.9.3](0.9.3.md). Nothing here is published; the owner decides when, and under
which number, this cohort is released.

## Moving from 0.9.3

Nothing to do for a host with one issuer.

A host that called `AddMPCoreBearerAuthentication` twice, once per issuer, never worked: the second scheme
kept no authority and no issuer. It now fails at that second call. Replace both calls with one call of
`AddMPCoreBearerIssuers`, as below.

## New

| Package | What it adds |
|---|---|
| `MPCore.Security.AspNetCore` | **Several token issuers.** `AddMPCoreBearerIssuers(issuers => issuers.Add("<scheme>", options => ...))`: one bearer scheme per issuer, each with its own authority or metadata, issuer, audiences and keys and every rule of ADR-007 section 6, behind a default scheme (`Bearer`) that picks the issuer a token names. A token is checked only against the keys of that issuer; a token that names no configured issuer is refused with `401`. Startup fails when two schemes name one issuer. ADR-016 |
| `MPCore.Security.AspNetCore` | **A second token as evidence.** `IMPCoreBearerTokenValidator.ValidateAsync(token)` validates a token of any configured issuer with that issuer's own parameters, keys refreshed from its metadata, and returns the validated issuer, the scheme and the claims, or a fixed reason. The token never becomes `CurrentActor` and is never logged. Registered by both `AddMPCoreBearerAuthentication` and `AddMPCoreBearerIssuers` |

| `MPCore.Security.Abstractions` | `SubjectEvidence`, a bounded record of the person behind a service's call (subject, session, issuer, authentication time), and `ISubjectEvidenceAccessor` |
| `MPCore.Security.AspNetCore` | **A person's token as evidence beside the service's identity.** Calling side: `AddMPCoreSubjectEvidence()` on a client's builder carries the token of the user being served in `x-subject-token`, never as the call's credential, over HTTPS only. Called side: `AddMPCoreSubjectEvidenceValidation(...)` and `UseMPCoreSubjectEvidence()` admit only listed services, validate the token with the host's issuer rules, `azp`, `typ`, `sid` and `auth_time` age, remove the header before any application code, and expose `SubjectEvidence`. A command requires it with `RequireSubjectEvidence("<issuer scheme>")`; a refusal is `403` / `PermissionDenied`. ADR-014, addendum of 2026-10-08 |

| `MPCore.Security.AspNetCore` | **Mutual TLS between services.** `AddMPCoreMutualTls(...)`: every TLS listener requires a client certificate whose chain ends at a configured authority (never the system store), valid now and for client authentication, with a listed workload name (URI or DNS subject alternative name), checked at the handshake; revocation as configured. `RequireWorkloadCertificate()` on an endpoint, with `UseMPCoreMutualTls()`, refuses a request without one with `401` / `Unauthenticated`. `UseMPCoreCertificateForwarding()` reads a certificate a proxy forwards in `X-Client-Cert`, only from `TrustedProxies`. The certificate never becomes the current actor. ADR-017 |
| `MPCore.Resilience.Http` | `AddMPCoreClientCertificate(...)` on a client's builder: presents a certificate from PEM files or one the host loads, and trusts only the configured authorities for the called service's certificate |
| `MPCore.Templates` | `Security:MutualTls` in `appsettings.json`, off by default; the generated host calls `AddMPCoreMutualTls` when it is on, and has `UseMPCoreCertificateForwarding()` and `UseMPCoreMutualTls()` in its pipeline, which do nothing while it is off |

How to consume several issuers:

```csharp
builder.Services.AddMPCoreBearerIssuers(issuers =>
{
    issuers.Add("staff", options =>
    {
        options.Authority = builder.Configuration["Security:Issuers:Staff:Authority"];
        options.ValidAudiences.Add("orders-api");
    });
    issuers.Add("partners", options =>
    {
        options.Authority = builder.Configuration["Security:Issuers:Partners:Authority"];
        options.ValidAudiences.Add("orders-api");
    });
});
```

How to run exactly one commit of `main`: every package records the commit it was built from, in its nuspec
and as `+<commit>` in every assembly's informational version. Copy `eng/consumer/MPCore.PinnedCommit.targets`
into the consuming repository, import it from `Directory.Build.targets`, and set `MPCorePinnedCommit` to the
full commit: the build fails when a restored MP Core package records another. `docs/guide/packages.md`,
"Which commit a package was built from".

| Where | What it adds |
|---|---|
| Continuous integration | `eng/check-version-moved.sh`: fails when shipped code changed since the published version that the source still declares. It has a self-test, and checks out the whole history |
| `release.yml` | A prerelease of a `main` commit, `<declared>-main.<n>`, `n` being the commit's place in `main`'s history; refused from any other branch and for any other suffix. The version check, the commit check of the release gate (`MPCORE_EXPECTED_COMMIT`) and the consumer check run before anything is published |
| `eng/verify-release-artifacts.sh` | Every package records one source commit, and every assembly carries `+<commit>`; self-test case 13 is a package that records another commit. A prerelease of `main` is verified with the declared version embedded in its template and CLI |
| `eng/consumer/MPCore.PinnedCommit.targets`, `eng/verify-consumer-pin.sh` | The consumer-side check, and its proof against packed packages in a throw-away NuGet cache |

## Changed

| What | Now |
|---|---|
| The cohort version | moves to `0.9.4` in every place it is declared. `0.9.3` was published from `bd41bd3`, and shipped code changed after it. The API baseline stays `0.9.3` |
| A second call of `AddMPCoreBearerAuthentication` | throws `InvalidOperationException` that names `AddMPCoreBearerIssuers`. Before, it registered a scheme without an authority, and the audiences of both calls accumulated |

How to carry a person's token as evidence:

```csharp
// The calling service
builder.Services.AddMPCoreResilientHttpClient("payments", client => client.BaseAddress = paymentsAddress)
    .AddMPCoreServiceIdentity(options => { /* the service's own client credentials */ })
    .AddMPCoreSubjectEvidence();

// The called service
builder.Services.AddMPCoreSubjectEvidenceValidation(options =>
{
    options.TrustedServiceClients.Add("orders");
    options.AllowedAuthorizedParties.Add("web-app");
    options.MaximumAuthenticationAge = TimeSpan.FromMinutes(10);
});
app.UseAuthentication();
app.UseMPCoreSubjectEvidence();
app.UseAuthorization();
// A command that needs the person:
options.AddPolicy("refund", policy => policy.RequireAuthenticatedUser().RequireSubjectEvidence("staff"));
```

## Known limits

| Limit | What to do |
|---|---|
| With mutual TLS on, every TLS listener of the host requires a client certificate | keep a listener for callers without one in cleartext behind the platform's network |
| `AddMPCoreMutualTls` sets Kestrel's HTTPS defaults | a host that calls `ConfigureHttpsDefaults` itself replaces one or the other; a listener declared in code is declared after `AddMPCoreMutualTls` |
| Wildcard DNS names in a workload certificate are not expanded | list the exact names |
| A backend generated from the template, with mutual TLS on, was not run in this change | the template's wiring is held by `TemplateContractTests`; the generated backend's build is part of the release procedure |
| Evidence travels one hop | a service called with evidence does not carry it further |
| The person's token must name the called service in its audience | configure the audience at the identity provider |
| A refusal of a call without a client certificate under mutual TLS is not part of evidence | mutual TLS between services is a separate change |
| MP Core's audit trail records the caller, the service | record the person from `SubjectEvidence` in the command's own business audit record |
| The generated host wires one issuer from `Security:Authority`; `mpcore configure --security-authority` sets one value | a product with several issuers replaces the `AddMPCoreBearerAuthentication` call of its `Program.cs` |
| A token is routed by the issuer its options name (`ValidIssuer`, else `Authority`) | when a provider's issuer differs from the address of its metadata, set `ValidIssuer` |
| Encrypted tokens (JWE) name no readable issuer | they are refused, as before |
| A prerelease's template and CLI embed the declared version (`0.9.4`), and the manifest of a backend generated from them names it | pin the prerelease with `--mpcore-version <version>-main.<n>` |
| A prerelease number is a commit's place in `main`'s history; a history rewritten to fewer commits would number a new commit below an older prerelease | nuget.org refuses the same version twice; never rewrite `main` once a prerelease is published |
| Nothing is published by itself | the owner starts `release.yml` for each commit he wants as a package |
| Packages built from a working tree with uncommitted changes record `HEAD` | the release workflow builds a fresh checkout; a local pack is a verification candidate only |
