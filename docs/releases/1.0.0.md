# MP Core 1.0.0 (not yet released)

The first version that makes a promise. From here a patch fixes, a minor version adds, and a break waits for the next
major version (README, Versioning; [ADR-020](../decisions/ADR-020-the-compatibility-promise-of-1-0.EN.md)). The public
API was decided once, type by type ([the review](../api/1.0-review.md)): 34 types and 2 members became internal, and 227 types stay.

A product that moves from 0.9.3 reads this page. It follows [0.10.1](0.10.1.md), which followed
[0.10.0](0.10.0.md). Nothing here is published; the owner decides when.

## Moving from 0.9.3

Three entries change behaviour for a product that did not read the notes of 0.10.0; each says what changed, why and
what to do. The notes of [0.10.0](0.10.0.md#moving-from-093) give the long form, with the steps to keep the Persian
texts.

**`CurrentActor.AuthenticatedAt` is when the person authenticated, and null when the token does not say.** It is
read from `auth_time` only. Before, a token without `auth_time` gave its issue time, so a token refreshed long after
the person signed in looked freshly authenticated. Code that judged how recently a person signed in keeps reading
`AuthenticatedAt`, or calls `IsAuthenticationFresh(maximumAge, now)`, which is never true without an authentication
time; code that wanted the issue time reads `IssuedAt`.

**A second call of `AddMPCoreBearerAuthentication` fails.** It never worked: the second scheme kept no authority and no
issuer. A host with two issuers replaces both calls with one call of `AddMPCoreBearerIssuers`.

**MP Core's own messages are English only.** English is the only built-in language and the default; a product decides
its own languages in its own repository (ADR-012, amendment of 2026-10-08). `MPCore.Localization` no longer carries the
Persian translation of MP Core's keys that 0.9.x shipped, so a product that relied on it receives English for those
keys. To keep the Persian texts the product copies `MPCoreMessages.fa.resx` from the 0.9.3 source into its own
repository and registers it with `AddMPCoreMessageCatalog(catalog => catalog.AddResources<...>())`.

The masking of more names, the generated host's console, the dependency of `MPCore.Observability` on `MPCore.Application`
and the module rules (rows of the table above) need no step of their own: they widen what is masked or add to what is
generated, and a repository generated before keeps what it has.

## Moving from 0.10.x

**34 public types became internal.** The public API of 0.10.1 had 261 types, and a product that builds on MP Core for
years needs to know which of them it may depend on. The review applied one rule: a type stays public only if the guides
document it, the template, a skill or a reference sample uses it, it appears in the signature of a kept member, or it is a
documented extension point a product implements. Everything else is internal, shared between the packages of the
cohort. The review found none of the 34 documented, used by the template, a skill or a reference sample, or named by a
kept signature. If you used one, the table says what to use instead. A type made public again later is an addition,
which a minor version may make.

| Type made internal | Use instead |
|---|---|
| `IIdempotencyKeySource`, `NoIdempotencyKeySource`, `GrpcIdempotencyKeySource`, `HttpIdempotencyKeySource` | Nothing to implement: the transport reads the key. `RequireIdempotencyKey()` on an endpoint, or `[RequireIdempotencyKey]` on a gRPC method, makes it required |
| `IIdempotencyScopeProvider`, `CurrentActorIdempotencyScope` | Nothing: a key is scoped to the current actor |
| `IIdempotencyStore`, `EntityFrameworkIdempotencyStore<TContext>`, `IdempotencyPurger<TContext>`, `IdempotencySaveChangesInterceptor`, `IdempotencyKeyConflictException` | `AddMPCoreIdempotency<TContext>()` registers them, `ApplyMPCoreIdempotency()` maps the tables, `UseMPCoreIdempotency(provider)` adds the interceptor |
| `IdempotencyContext`, `IdempotencyEntry`, `IdempotencyRequest`, `IdempotentExecutor`, `IdempotencyServiceCollectionExtensions` | `IIdempotentExecutor.ExecuteAsync`, registered by `AddMPCoreIdempotency<TContext>()` |
| `SensitiveMessageTypes`, `GrpcSensitiveMessageOptions` | `AddMPCoreSensitiveMessageTypes(...)` for a type, `AddMPCoreSensitiveMessages("package.Service")` for a gRPC service |
| `AuditMasking`, `AuditSaveChangesInterceptor` | `MaskStyle` in an `AuditPolicy`; `AddMPCoreAudit<TContext>()` and `UseMPCoreAudit(provider)` |
| `MessageTranslationRefresher<TContext>` | `AddMPCoreMessageTranslations<TContext>()` registers it |
| `AggregateEventBridgeExtensions` | `AddMPCoreWolverineDbContext<TContext>()` already applies it |
| `ObservabilityPlan`, `ResolvedDestination` | `MPCoreObservabilityOptions`, read by `AddMPCoreObservability` or `AddMPCoreFoundation` |
| `SensitiveActivityProcessor`, `SensitiveLogRecordProcessor`, `SensitiveDataPolicy` | `AddMPCoreObservability` registers the processors; `RedactionOptions` (`Enabled`, `AdditionalSensitiveFields`) configures them |
| `IServiceTokenSource` | `AddMPCoreServiceIdentity` on a client's builder |
| `MPCoreRoleRequirement`, `ScopeRequirement`, `ResourceKeyRequirement`, `SubjectEvidenceRequirement`, `WorkloadCertificateRequirement` | `RequireMPCoreRole(...)`, `RequireScope(...)`, `RequireResourceKey("<key>")`, `RequireSubjectEvidence(...)`, `RequireWorkloadCertificate()` |
| `SubjectEvidenceHeader` | The header is `x-subject-token`; `AddMPCoreSubjectEvidence()` carries it |

**2 public members became internal.** `HandlerActorScope.ActorName(envelope)` and `HandlerTenantScope.TenantOf(envelope)` were
static helpers that the scopes' own `For` method called and nothing else did: no guide, template, skill or reference sample
uses them, and the middleware that Wolverine's generated code calls does not need them public. The Wolverine middleware
classes themselves stay public.

**A direct `Render` refuses a typed argument name that is not an argument name.** `Render(key, arguments, typedArguments,
culture)` now does what `FailureMessageDescriptor` does: it requires a lower-case letter followed by lower-case letters, digits
or underscores. Before, only a
missing value and a repeated name were refused, and the name reached the warning log and the metric tag `argument` when a
formatter failed. The rule ends the name with `\z`, so `"x\n"`, which the descriptor accepted, is refused as well. What to do:
name typed arguments as their placeholders are named.

**A repository generated by `mpcore new backend` and 0.10.1 holds two solution files.** Delete `<Organization>.<Component>.Backend.sln` at its
root. That tool created a solution file of its own beside the template's `<Organization>.<Component>.slnx`, and with two,
`dotnet build` at the root fails with `MSB1011`. The `.slnx` lists exactly the projects that were generated.

**Building MP Core itself needs a checked baseline.** Run `./eng/restore-api-baseline.sh` once per checkout and again when
`MPCoreBaselineVersion` moves: a build of a runtime package fails without its checked baseline. For work offline,
`-p:MPCoreOfflineWithoutApiBaseline=true` builds without it, with a warning, and fails in CI.

## Changed

| What | Now |
|---|---|
| API validation | is never skipped in silence, and never in CI or the release. A build of a runtime project fails unless its package of the baseline version is in `artifacts/packages`, was checked, and is still the package that was checked; the one switch for work offline, `-p:MPCoreOfflineWithoutApiBaseline=true`, warns for every package and fails in CI. The script downloads each package from nuget.org only, and accepts it only with `dotnet nuget verify --all`, a repository signature whose certificate nuget.org lists, and the commit of the tag of that version. Before, a clean checkout validated nothing and printed that it had skipped. ADR-010, addendum of 2026-10-12 |
| The API baseline of this cohort | `MPCoreBaselineVersion` is `0.10.1`, the last published version. The 34 types made internal are recorded as breaks against it, each with its reason, in `src/<package>/CompatibilitySuppressions.xml`; the files go with the release of 1.0.0, which becomes the baseline |
| CI and the release | restore and check the baseline before they build, with the tags, after the script's self-test. They run the per-package check alone; **require mode for the whole restore is not switched on**: it fails on macOS for four third-party packages with expired signatures, and has not been run on GitHub's runner |
| `NuGet.config` | lists nuget.org only. The baseline folder was a package source for `MPCore.*` |
| The contract of the tool and the template | `docs/contracts/cli.json` and `template.json` record every command, option, default and probed exit code of the tool and the manifest it writes, and every parameter of the template and the files it generates for each shape and transport. Tests generate them by running the built tool and the template, fail when they differ, and fail when a fact of the file at the baseline tag is gone unless the version may break it. ADR-004, addendum of 2026-10-12 |

| The compatibility promise | README, Versioning, states what 1.0.0 promises and how a version may change it; ADR-020 gives the reasons. The public API is recorded in `PublicAPI.Shipped.txt`, and the build fails on an undeclared change |

## Fixed

| Where | What was wrong | Since |
|---|---|---|
| `mpcore new backend` left two solution files | after generating, it created a solution file of its own beside the template's `<Product>.slnx`, so the repository held two and `dotnet build` at its root failed with `MSB1011`. ## Known limits

## Checking a download

The release run freezes the SHA-256 of every package it built in `SHA256SUMS.txt`, uploaded with the packages
as the run's artifact. The sums are of the packages as the release run built them. nuget.org adds its
repository signature (`.signature.p7s`) to every package after upload, so a downloaded file has another
SHA-256. To check a download, verify its signatures with `dotnet nuget verify --all <file>` and compare its
entries other than `.signature.p7s` with the built package.
