# MP Core 0.10.2 (not yet released)

A patch version: two defects of the command line tool are fixed, API validation can no longer be skipped, the tool
and the template get a recorded contract, and a typed message argument is checked for its name. It follows
[0.10.1](0.10.1.md). Nothing here is published; the owner decides when, and under which number, this cohort is
released.

## Moving from 0.10.1

| If you | Do |
|---|---|
| generated a backend with 0.10.1 using `mpcore new backend` | delete `<Organization>.<Component>.Backend.sln` at its root. That repository holds two solution files, and `dotnet build` at its root fails with `MSB1011`. `<Organization>.<Component>.slnx` is the one that stays |
| build MP Core itself | run `./eng/restore-api-baseline.sh` once, and again when the baseline version moves: a build of a runtime package fails without its checked baseline. For work offline, `-p:MPCoreOfflineWithoutApiBaseline=true` builds without it, with a warning, and fails in CI |
| use a typed message argument in a direct `Render` | give it a name that is a lower-case letter followed by lower-case letters, digits or underscores. Any other name now throws `ArgumentException` |

Nothing else changes in a product.

## Fixed

| Where | What was wrong | Since |
|---|---|---|
| `mpcore new backend` | after generating, it created a solution file of its own beside the template's `<Product>.slnx`, so the repository held two and `dotnet build` at its root failed with `MSB1011`. It now uses the template's, and refuses a template that did not generate exactly one (exit code 4) | 0.10.1 |
| `mpcore configure --cache`, `--business-audit`, `--timeseries` | stopped with exit code 7 ("these files differ from what the generator produced") on a repository nobody had edited, because every generation writes a new random `UserSecretsId` into the host project and the regenerated reference differed in that line. Had it applied, the project would have got another id and the secrets stored under the old one would have been orphaned. The reference now takes the repository's id | 0.10.0 |

## Changed

| Area | Now |
|---|---|
| API validation | is never skipped. A build of a runtime project fails unless its package of the baseline version is in `artifacts/packages`, was checked, and is still the package that was checked; the message names `./eng/restore-api-baseline.sh`. The script downloads each package from nuget.org only and accepts it only with `dotnet nuget verify --all`, a repository signature whose certificate nuget.org lists in its service index, and the commit of the tag of that version. Before, a clean checkout validated nothing and printed that it had skipped. ADR-010, addendum of 2026-10-12 |
| The API baseline | `MPCoreBaselineVersion` is `0.10.1`, the last published version |
| CI and the release | restore and check the baseline before they build, with the tags, after the script's self-test. They run the per-package check alone; **require mode for the whole restore is not switched on**: it fails on macOS for four third-party packages with expired signatures, and has not been run on GitHub's runner |
| `NuGet.config` | lists nuget.org only. The baseline folder was a package source for `MPCore.*` |
| The contract of the tool and the template | `docs/contracts/cli.json` and `template.json` record every command, option, default and probed exit code of the tool and the manifest it writes, and every parameter of the template and the files it generates for each shape and transport. Tests generate them by running the built tool and the template, fail when they differ, and fail when a fact of the file at the baseline tag is gone unless the version may break it. ADR-004, addendum of 2026-10-12 |
| A typed message argument | a direct `Render(key, arguments, typedArguments, culture)` refuses a name that is not an argument name, as `FailureMessageDescriptor` does, before anything is rendered. The rule ends the name with `\z` in both places: `"x\n"` was accepted by the descriptor and would have reached a log line and a metric tag |
| The guides of a generated backend | say that a module's projects are added to the solution with `dotnet sln add`, and why: `dotnet test` at the root runs only the tests the solution lists |

## Known limits

| Limit | What to do |
|---|---|
| `eng/restore-api-baseline.sh` is a bash script and was run on macOS and Linux; Windows was not run | on Windows, run it in Git Bash or WSL |
| Require mode for the whole restore is off | the baseline, which is what a release is compared with, is checked package by package on every operating system; third-party packages keep NuGet's default verification |
| The contract files do not record the words of messages, or exit codes of situations the tests cannot set up | see `docs/contracts/README.md` |
| ADR-009 still names `<Product>.Backend.sln` as the generated solution | an accepted record; its table is corrected only with the owner's word |

## Checking a download

The release run freezes the SHA-256 of every package it built in `SHA256SUMS.txt`, uploaded with the packages
as the run's artifact. The sums are of the packages as the release run built them. nuget.org adds its
repository signature (`.signature.p7s`) to every package after upload, so a downloaded file has another
SHA-256. To check a download, verify its signatures with `dotnet nuget verify --all <file>` and compare its
entries other than `.signature.p7s` with the built package.
