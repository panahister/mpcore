# ADR-012 — One project per module; business rules, input validation and messages as first-class model

- Status: Proposed; pending owner acceptance
- Date: 2026-09-27
- Extends: ADR-006 (transport-neutral failures), ADR-009 (generation topology), ADR-011 (application execution model)

## Context

The Commerce backend of the Storefront sample was the first modular monolith generated by the template
and run end to end. Its review found four structural problems that the template and the framework, not
the use case, had caused.

1. **Sixteen projects for four modules.** The template prescribed three projects per bounded context
   (Domain, Application, Infrastructure) and still generated a root `Domain` and `Application` project,
   which stayed empty. Most module projects held one or two files. Adding a module cost three project
   files.
2. **No rule model in use.** `MPCore.Domain` shipped `IBusinessRule`, `BusinessRules.Check`, `ValueObject`
   and `Entity<TId>`, but nothing in the template or the skills asked for them. The sample returned error enums
   from its aggregates, kept prices as `decimal` and phone numbers as `string`, and had no child entity.
   `IBusinessRule` itself carried a developer message and a code, but no error domain and no message key,
   so every broken rule reached a caller as the same generic `mpcore.domain` failure with one generic text.
3. **No input validation model.** Handlers validated request shape by hand, each in its own way.
4. **Messages were unrenderable.** ADR-006 and ADR-008 made every failure carry a message key instead of a
   sentence, and both transports negotiated a culture from `Accept-Language`, but the only localizers were
   `Null` implementations. No MP Core host had ever shown a caller a message text. The owner asked for
   texts an administrator can translate at run time.

## Decision

### 1. A module is one project, with the layers as folders

For `shape=modular-monolith`, a bounded context is one project `src/Modules/<Context>/<Product>.Modules.<Context>`
holding `Domain/`, `Application/` and `Infrastructure/` folders, plus a `<Product>.Modules.<Context>.Contracts`
project only when other modules call it. The root `Domain` and `Application` projects are not generated
for this shape. A module references MP Core abstraction packages, its own Contracts and other modules'
Contracts, never another module's main project and never the host.

The compiler enforces the boundary between bounded contexts, which Eric Evans (*Domain-Driven Design*,
2003) defines as the limit of one model and one language, and which is the boundary that lets modules
change independently. The boundary between layers inside a module is enforced by architecture tests on
namespaces. This is Simon Brown's *package by component* ("The Missing Chapter" in Robert C. Martin's
*Clean Architecture*, 2017), chosen over the two alternatives:

| Layout | Projects for four modules | Boundary between modules | Boundary between layers |
|---|---|---|---|
| Three projects per module (Kamil Grzybek's *Modular Monolith with DDD*; eShop's Ordering) | 12 | compiler | compiler |
| Three shared projects, modules as folders (Jason Taylor's and Ardalis's Clean Architecture templates, which model one context) | 3 | tests only | compiler |
| **One project per module, layers as folders** | 4 plus Contracts | **compiler** | tests only |

Handlers, messages, ports and adapters stay `public`: Wolverine generates handler code in a separate
assembly, so `internal` cannot be the module boundary. Project references are.

### 2. Application folders and one use case per file

`Application/` holds `Commands/`, `Queries/`, `Views/`, `Ports/`, `Process/` and `Validators/`. A command
or query record and its handler share one file (Jimmy Bogard's *Vertical Slice Architecture*, 2018;
Wolverine's own convention). Command-query separation follows Bertrand Meyer and Greg Young, as in eShop's
Ordering service. `Views/` holds what a query or command returns (a read model, a DTO). `Ports/` follows
Alistair Cockburn's *Ports and Adapters* (2005). `Process/` holds process managers (Gregor Hohpe and Bobby
Woolf, *Enterprise Integration Patterns*, 2003), which choose the next command while the aggregate keeps
the rules. Namespaces follow folders.

A query only reads. It declares no `IUnitOfWork`, publishes nothing, and reads through a read-model port
that returns views, never through a repository. It is the only thing an HTTP `GET` sends, because RFC
9110 requires `GET` to be safe. A read with a consequence is two messages: a query and a command.

### 3. Business rules carry an error domain, a code and a message key

`IBusinessRule` gains `ErrorDomain`, `MessageKey` and `MessageArguments`, with default implementations so
existing rules compile unchanged. A new base class, `BusinessRule`, validates the three identifiers at
construction with the same patterns `ErrorIdentity` and `FailureMessageDescriptor` use, so a malformed
identifier fails in the first unit test. `Entity<TId>.CheckRule(rule)` checks a rule inside the aggregate.

Both transports map `BusinessRuleValidationException` to a failure under **the rule's own** domain and
code, with the rule's message key and arguments, category `BusinessRule` (REST 422, gRPC
`FailedPrecondition`). A rule that implements the interface directly and returns malformed identifiers is
mapped to the previous generic identity, never to an exception in the transport.

`UseMPCoreWolverine` registers `OnException<BusinessRuleValidationException>().MoveToErrorQueue()`
before the product's own rules: a broken rule is a verdict about the current state, and retrying it
replays the verdict. The named-rule pattern is Kamil Grzybek's; keeping the invariant inside the
aggregate is Evans's and Vaughn Vernon's (*Implementing Domain-Driven Design*, 2013); Vladimir Khorikov
names the result the *always-valid domain model*.

### 4. Input validation is FluentValidation, run before the handler

A new package, `MPCore.Validation.FluentValidation`, wraps Jeremy Skinner's FluentValidation (Apache-2.0)
through Wolverine's `WolverineFx.FluentValidation` middleware. `UseMPCoreFluentValidation()` replaces the
middleware's failure action: an invalid message never reaches its handler, and the caller receives MP
Core's validation failure (`mpcore.validation` / `VALIDATION_FAILED`, category `Validation`) with one
`FieldViolation` per failure. The field path is the property path in lower_snake_case; the rule code is
`WithErrorCode(...)` or the validator's name (`NotEmptyValidator` → `NOT_EMPTY`); the message key is
`WithMessage(...)` when it is a key, otherwise `validation.<rule_code>`; the arguments carry the field and
the rule's limits, never the value the caller sent. `AddMPCoreValidators(assembly)` registers a module's
validators by type. The template registers validators for every assembly in `HandlerAssemblies.All`.

A validator checks the shape of a request. A check that needs state is a business rule and belongs in the
aggregate; the Application project cannot reach the database from a validator by construction. This is
the division Microsoft's eShop applies to its Ordering commands, and the reason Khorikov keeps
FluentValidation out of the domain.

### 5. Messages are rendered by a catalog, at the edge

`MPCore.Application` gains `IFailureMessageLocalizer`, the transport-neutral port. `IHttpFailureLocalizer`
and `IGrpcFailureLocalizer` keep their shape; their default implementations now delegate to the neutral
port when one is registered, and render nothing otherwise, exactly as before.

A new package, `MPCore.Localization`, implements it as a **message catalog** over `IMessageTemplateSource`s
ordered by precedence: MP Core's own texts (−100; English and Persian ship in the package), the product's
resource files (0), and administrator overrides (100). Rendering walks the requested culture, its parents,
the default culture and the neutral text, exactly as .NET's `ResourceManager` does, and substitutes
named placeholders (`{limit}`) so a translator may reorder them. A key with no template anywhere renders
nothing, increments `mpcore.localization.missing` and is logged once. `IsKnownKey` answers whether a key
has a default text, so an administrator can only translate keys the code uses. MP Core's observability
now exports every `MPCore.*` meter.

A second package, `MPCore.Localization.EntityFrameworkCore.PostgreSql`, follows the audit package's shape:
a `localization.translations` table applied to the product's own context
(`ApplyMPCoreLocalization`), an `IMessageTranslationStore` port whose changes commit in the handler's own
transaction (ADR-011: the store never saves), and a hosted refresher that reloads the in-memory override
source on every instance when the table's row count or latest modification time changes. The hybrid
cache was not used for this, because its in-process level would keep the other instances stale until
expiry; a periodic check of a small table reaches every instance within one interval. The product owns
the commands and the UI that call the store.

The design follows RFC 9457, which keeps `title` and `detail` for people and codes for programs; ASP.NET
Core's `IStringLocalizer` model, which makes the text source replaceable; and ABP Framework's Language
Management module, which stores administrator translations in the database.

### 6. The template and the skills teach all of this

`src/Modules/README.md` in the template describes the layout, the folders, the rule and message model, and
names the source of every convention. `docs/architecture.md` gains "Business rules, validation and
messages". `docs/capabilities.md` lists the new capabilities. The skills `mpcore-plan-bounded-context`,
`mpcore-implement-ddd-module`, `mpcore-implement-vertical-slice`, `mpcore-integrate-contexts` and
`mpcore-verify-business-behavior` prescribe the same. The generated host registers the catalog and the
validators for every shape.

### 7. Between modules: a module writes only its own data

Added after a design review of the sample's checkout. Checkout was one Ordering
transaction that emptied the basket and registered the payment through interfaces the Basket and Payments
modules published in their Contracts. It was atomic, and it was exactly the part that would have to be
redesigned on the day one of the three modules became a service.

A module writes only its own data. There are two ways for it to make another module change, and the
framework supports both:

| | A message | A call through Contracts |
|---|---|---|
| What it is | The module publishes a module message in its own transaction (the transactional outbox). The other module handles it from a durable local queue, in a transaction of its own. | The module calls an interface the other module publishes and implements, inside the caller's transaction. |
| Consistency | Eventual. The caller's answer can say "accepted", not "done". | Immediate. Both changes commit together or not at all. |
| What the receiver must be | Idempotent by a business key, because a message can arrive twice. | Nothing more than correct. |
| A refusal by the other module | Arrives later, as a message, and is answered with a compensation. | Is the caller's own failure, returned at once. |
| When a module becomes a service | The message changes its transport. | The transaction has to be redesigned. |

**The default is a message.** Vaughn Vernon's aggregate rule (*Implementing Domain-Driven Design*, 2013)
is one aggregate per transaction and eventual consistency between aggregates. Kamil Grzybek's *Modular
Monolith with DDD* integrates modules through events only, so that a module can be extracted without
touching the others. Microsoft's eShop checks out this way: the Basket publishes a checkout event that
carries a snapshot of the basket, and Ordering creates the order from it. Gregor Hohpe and Bobby Woolf
(*Enterprise Integration Patterns*, 2003) name the receiving side the Idempotent Receiver and the class
that drives the steps the Process Manager.

**A call through Contracts that writes is a deliberate exception**, for two modules that must change
together and that are meant to stay in one deployment. It costs nothing until that stops being true. The
module guide asks for the reason to be written where the interface is declared.

**A call through Contracts that reads is always acceptable.** It couples nothing that a cache or a local
copy could not later replace.

Three consequences follow for the module that publishes a message, and the module guide states them:

- The message carries a **snapshot**, everything the receiver needs, so the receiver never calls back.
- What only the receiver can refuse is refused **after** the caller has been answered. The publisher
  therefore checks at its own edge what it can, and a test holds the two modules' rules together (Ian
  Robinson, *Consumer-Driven Contracts*, 2006).
- A secret in a module message stays in the host: module messages are not integration events and are
  never routed to a broker.

The sample applies the default everywhere: checkout is a Basket command that publishes `BasketCheckedOut`, and
its Contracts projects publish one interface, a read. A later use case will show the exception.

## Consequences

- Three new runtime packages: 27 runtime packages, 29 with the tools. They have no alpha.9 baseline, so
  API-compatibility validation reports them as new rather than skipped (`NEW_IN_COHORT`).
- `IBusinessRule` gains members with default implementations; `Entity<TId>` gains a protected static
  method. Existing consumers compile unchanged. The package-validation result is recorded in the release
  notes.
- A generated modular monolith no longer contains a root `Domain` or `Application` project. A product
  generated from an earlier template keeps its layout; nothing forces a migration.
- The cohort declared in code is still `0.2.0-alpha.9`, which is published and immutable (ADR-010). These
  changes ship in the next unused prerelease version, together with the fixes the sample found earlier.

## Verification

- `MPCore.Domain.Tests`: rules carry identifiers, aggregates do not change on a broken rule, malformed
  identifiers and oversized arguments fail at construction.
- `MPCore.Transport.Http.Tests` and `MPCore.Transport.Grpc.Tests`: a broken rule reaches the caller under
  its own domain, code and localized message; malformed rules still produce a valid problem; the Domain
  package accepts exactly the identifiers the failure model accepts.
- `MPCore.Messaging.Tests`: a queued message that breaks a rule is attempted once and dead-lettered, even
  when the host adds a catch-all retry (seen failing with four attempts without the rule); and the
  validators run before a handler that declares `IUnitOfWork`, which the rollback policy's old frame
  placement prevented (the handler ran on an invalid command and was validated after).
- `MPCore.Validation.Tests`: conversion of paths, codes, keys and limits; the caller's value is never
  carried; an invalid message never reaches the handler under Wolverine's `NotAllowed` service-location
  policy; every built-in validator has an English and a Persian default text.
- `MPCore.Localization.Tests`: culture chain, overrides, placeholders, missing-key metric and log, REST
  `detail` in the negotiated language, and stored translations against a real PostgreSQL database,
  including an uncommitted change that is never served.
- The sample (section 7): `CheckoutHandlerTests`, `CheckoutProcessTests`, `CheckoutContractTests`, and three
  architecture tests: the Contracts projects publish no interface that writes, a handler takes
  repositories of its own module only, and no foreign key crosses a schema.
- `TemplateContractTests`: the root projects are excluded for the modular monolith, every reference to
  them sits inside the service-only condition, every host registers the catalog and validators, and the
  module guide names its sources. Both shapes were generated from the changed template and built from
  MP Core source with zero errors.
